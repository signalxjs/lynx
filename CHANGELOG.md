# Changelog

All notable changes to this repository are documented here. All `@sigx/lynx-*` packages share a single lockstep version — one entry per release covers every package.

## [Unreleased]

### Added

- **CSS `@media` / `@supports` / `prefers-color-scheme` now reach the device — theming can start moving out of JS signals** (#951). Three pieces, verified on both platforms with a release-build probe screen:
  - **`@sigx/lynx-plugin`**: `@lynx-js/template-webpack-plugin` bumped 0.11.0 → 0.15.0 (`@lynx-js/tasm` 0.0.49; the Node 20 pin that held it died with #957, and this is deliberately decoupled from the #975 rspeedy/rsbuild migration), plus a new `enableCSSRule` page-config flag (default `true`, kill switch). Both are required: media/supports encoding exists only from tasm 0.0.41, **and** only through the `CSSRuleParser` path gated on the undocumented `enableCSSRule` key — without it the encoder silently drops every at-rule, no diagnostic. Also guards the web target against tpwp ≥ 0.14's async-template pass crashing on lazy chunk groups whose JS deduplicated into the main chunk (`SigxWebEncodeGuardPlugin`). The web bundle still carries no media/supports rules — upstream's `WebEncodePlugin` drops them; web keeps the JS appearance path.
  - **`@sigx/lynx-appearance`**: the publisher now drives the engine's own color scheme (`LynxView.updateColorScheme`, "channel 0") on both platforms, and the CLI templates seed the initial value at LynxView construction — the engine never tracks the OS scheme by itself (negative-control-verified: without this wiring a dark device resolves light). On iOS, foreground appearance flips are now observed via `registerForTraitChanges` (iOS 17+); previously they reached neither JS nor the engine until the next app-foreground.
  - **Node 20 support is dropped** (agreed in #957, executed here): the tasm WASM encoder the new template-webpack-plugin ships needs a newer V8 than Node 20 ("Unknown heap type -14" on web builds). CI now tests Node 22/24 and `@sigx/lynx-plugin` declares `engines.node >= 22`.
  - Device verdicts: `prefers-color-scheme` correct at cold start and on live flips; width/orientation queries evaluate in **logical px** and re-evaluate live on rotation; stylesheet-declared and `@media`-scoped custom properties resolve and inherit (the pure-CSS theme-palette primitive #116 was missing); `@supports` matches honestly (no false positives, doesn't claim `oklch()`); `@font-face` loads via `data:` URIs (bundler-emitted `url()` assets don't resolve — the lynx-icons v1.1 path is inlining or native registration). Inline `--*` custom properties register only through runtime `SET_STYLE` styles, not snapshot-template static styles — `enableCSSInlineVariables` stays load-bearing for ThemeProvider; a CSS-first ThemeProvider is a follow-up. The showcase gains a permanent **CSS engine probe** screen (verdict swatches: green = works).

### Fixed

- **`@sigx/lynx-list`: chat first paint lands on the newest message on Android — and `bottomInset` starts working** (#930). Opening a chat whose history exceeds the viewport landed *near* the bottom but not at it, with the newest message(s) hidden behind the composer; sending one message snapped it right. Android's instant scroller is padding- and cell-height-blind — `UIList.scrollToPosition` computes `offsetPx += rv.getHeight() - dipToPx(itemHeight ?? 0)` and we never pass `itemHeight`, so it anchors the target cell's **top** at `paddingTop + viewportHeight` and the cell lands entirely below the visible edge. Device logs confirm it exactly: `scrollToPositionNoSmooth: position=52, offset=1914`, and 1914px is the viewport. `LinearLayoutManager.fixLayoutEndGap` only corrects a gap, never an overshoot, so nothing pulled it back. The instant pin is now two-phase: after `scrollToPosition` it consumes one clamped `scrollBy({ offset: viewport })` on the **next** `layoutcomplete` — `RecyclerView.scrollBy` stops at `getEndAfterPadding()`, so it is padding-aware and cell-height-agnostic and lands exactly at the end. The #839 re-pin skips the pin entirely and uses that one clamped call. Android only; iOS's scroller already uses the real cell height, and the smooth follow path was never affected.

  **This also revives `bottomInset`.** Its native compensation only runs when `wasPinned` — `pin && distanceFromBottom <= 1` — so a first pin that lands short left it permanently false: on Android the newest message never actually stayed clear of a keyboard or sheet, despite that being the whole point of the prop. With the pin exact it fires, device-confirmed against the showcase Chat composer's emoji sheet. See #973 for why this also blocked evaluating whether the `sigx-list` platform subclass can be retired.

- **`@sigx/lynx-list`: the pull-to-refresh indicator no longer paints at rest** (#754). A refresh-enabled `<List>` permanently showed `Refreshing…` (or the `refresh` slot) bleeding over whatever sat directly above it. The indicator is parked at `position: absolute; top: -pullThreshold` inside the content wrapper — outside that wrapper's bounds — and Lynx views default to visible overflow, so document order made it paint over the earlier sibling. The **measuring** wrapper now clips when `refreshEnabled`; it has to be that one and not the content wrapper, because the indicator is a child of the content wrapper and translates down with it, so clipping there would hide it during the pull too. `props.style` is spread after, so a caller can still opt out.

### Added

- **`@sigx/lynx-observability`: `Memory.query()` — what the Lynx engine is actually holding** (#953). The package captured errors but had no resource telemetry, and the repo had no JS-side memory instrumentation at all. One call now returns a process-global reading covering every LynxView: `totalBytes` against the app's own `appBytes`, the element tree as `elementBytes` **and** `elementNodeCount`, platform UI bytes, both runtime heaps, and a per-instance breakdown sorted by size. That element-bytes-against-node-count pairing is the signal #603 and #606 have been missing — it turns "the screen went blank" into "we're mounting 12,000 nodes".

  This gives the package its **first native code** (`signalx-module.json` + `ios/` + `android/`), because the reading cannot be had from JS: Lynx does emit a `memory` performance entry, but it sends it with `kEventTypePlatform` only, so it reaches native observers and never the background or main-thread JS runtimes. `MemoryUsageEntry` is nonetheless declared in `@lynx-js/types`, which makes `observe(['memory'])` type-check and return silence on device — a trap worth knowing about, and the reason a bridge of our own was the only route. Requires **Lynx ≥ 4.0.1** and a `sigx prebuild`; no engine setting is needed, since `enable_memory_monitor` gates only the passive entry stream and fetcher registration is unconditional.

  A `'timeout'` status is a **partial result, not an error** — `query()` resolves, and `completedInstanceCount` against `expectedInstanceCount` tells you how much of the reading you got. Device-verified on both platforms against release builds; the README records which fields each platform actually populates, because they differ (Android reports no `viewBytes`, iOS reports no background-runtime bytes, and only iOS fills in `url`). **Installing this package changes your OTA runtime fingerprint** — it adds native sources — so re-prebuild, cut a store release, and republish your update bundles.

- **`@sigx/lynx-observability`: `Memory.startReporting()` — memory on a timer, not just on demand** (#953). Samples engine memory on an interval and logs each reading under a `memory` namespace, so it reaches the `sigx dev` terminal and any registered sink with no extra wiring. Also reachable declaratively through `logging.production.memory` in `signalx.config.ts`, presence-means-enabled exactly like the existing `sink`.

  It reschedules from **completion**, not on a fixed interval — an engine query can take the full timeout, and `setInterval` would stack overlapping process-global collections. Every tick catches, because an unhandled rejection on the background runtime is a fatal main-thread exception under PrimJS (#863), not a warning someone might read. `maxInstances` (default 5) caps the per-instance rows so a record can't grow with the app's LynxView count. Unlike `Memory.query()`, it **no-ops instead of throwing** when the native module isn't linked: it's ambient telemetry started before app code runs, and a throw there would take down an app whose only mistake was forgetting to re-run `sigx prebuild`.

  **A wrapper for Lynx's background-thread `PerformanceObserver` was written for this release and then withdrawn**, because it doesn't work here. `lynx.performance.createObserver` exists, `observe()` succeeds, and no entry is ever delivered — not `pipeline`, not `metric`, and not the older `addTimingListener` callbacks either. Verified on a release build on device, with the raw engine API rather than only our wrapper. Shipping it would have been the exact failure mode this package documents elsewhere: an API that type-checks, reads correctly, and returns silence. First-paint and FCP reporting therefore isn't available yet; the finding is filed with its repro as #982.

- **`examples/flik`: stress harness and the measurement it was built for** (#937). Disc count up to 400, a broadphase toggle, a switch that defeats the dirty-write cull, and a `loop` mode that re-kicks at quiescence so the worst case is sustained rather than a decaying transient. The headline result, on a 120Hz Pixel 9 Pro XL release build: **up to 200 simultaneously moving discs the three render paths are indistinguishable** — publishing 200 SharedValue tuples per frame at 114fps is below what the instrument can resolve, which was not the expected answer, since the bridge publish was the suspected bottleneck going in. What does cost is the simulation, superlinearly with contacts: 0.2ms at 12 discs, 1.5ms at 200, 6.8ms at 400 where the board jams solid. A `0 writes` reading at 400 turns out to mean "the board settled and the dirty-write cull is doing its job", not "the bindings died" — the counter has two meanings and only the `all` toggle separates them.

- **`examples/flik`: switchable render paths** (#937). Three ways to get a disc's position onto the screen, chosen at runtime: a `SharedValue` with a `useAnimatedStyle` binding (the idiomatic path, which also publishes every write to the background thread), a raw `setStyleProperty` from the simulation, and the same binding over an *unbridged* `MainThreadRef` — which works because the style-binding flush resolves `refMap[wvid].current?.value` and never consults `bridgedAvWvids`, so the mapper runs with no publish. The third exists to split the first's cost between the mapper and the bridge. Switching remounts the disc layer so the losing path's bindings are genuinely unregistered rather than left idling in the flush loop. At the real game's twelve discs all three measure the same on a 120Hz Pixel 9 Pro XL (p50 5.8–6.0ms, tick 0.1–0.2ms) — twelve bridge tuples a frame is below what the instrument can resolve, which is itself the result.

- **`@sigx/lynx-plugin`: `__DEV_BUILD__`** (#937). A plain boolean build-tier literal, folded per environment alongside `__WEB__` / `__NATIVE__`. App code had no safe way to ask "is this a development build": the bare `__DEV__` define expands to a `process.env` expression that **throws in the Lynx background runtime** — the plugin's own comment already warned against referencing it, but offered nothing in its place. `__DEV_BUILD__` is resolved in Node at build time, so `if (__DEV_BUILD__)` both works at runtime and tree-shakes out of a release bundle. Declared in `@sigx/lynx/client`.

- **`examples/flik`: a frame-timing HUD** (#937). The repo's first performance instrumentation. It reports frame interval and tick cost as separate numbers, because their divergence is the whole diagnosis — a short tick inside a long frame means the time is going somewhere outside our control, while a tick that fills the frame means it is our JavaScript. Percentiles come from an 8-bucket histogram interpolated within the containing bucket, since the main thread's only clock is `Date.now()` at 1ms granularity and a precise percentile off it would be fiction. The sparkline is written one bar per frame straight from the worklet — one style write per frame regardless of disc count, and no background traffic, so it cannot distort what it displays; the numeric panel drains to the background thread at 2Hz. First reading, release build on a 120Hz Pixel 9 Pro XL at 12 discs: `120fps p50 6.0 p95 11.4 · tick 0.3/1.0ms`.

- **`@sigx/lynx-audio`: `Audio.subscribeInterruptions(cb)`** (#867). What happened to playback or recording during a phone call, an alarm, or another app taking the session was previously **undefined to the app** — and on Android nothing requested audio focus at all, so playback simply talked over calls and a recording could be silently ruined. Both platforms now report interruptions on one session-wide channel: iOS observes `AVAudioSession.interruptionNotification`, Android holds reference-counted audio focus for the lifetime of any player or recorder and maps focus loss/gain onto the same event. `{ type: 'began' | 'ended', shouldResume: boolean }`; returns an unsubscribe function per C7. A permanent loss reports `began` with no matching `ended`, which is accurate — the session isn't coming back on its own.

- **`examples/flik`: the flick gesture — FLIK is playable** (#937). You put a finger on one of your discs, slide it anywhere inside your own end of the board, and throw it; the release velocity of your hand IS the shot, so there is no aim line and no power meter. All of it runs on the main thread — `onEnd` has the velocity in hand, writes it into the disc and arms the frame loop in the same frame the finger lifts, and the background thread is told afterwards purely so the ruleset can record which disc was launched. Disc size is felt at both ends: a big disc leaves the finger slower for the same flick (same effort, more mass) and hits harder when it arrives, netting about half again the momentum. Sliding costs nothing — only a flick above the minimum speed commits a turn.

- **`examples/flik`: a main-thread physics simulation** (#937). The FLIK example gained the simulation half of its reason to exist: a fixed-timestep integrator, uniform-grid broadphase and elastic collision resolution, all running as `'main thread'` worklets driven by `useFrameCallback` (#933). It is the repo's first sustained 60 Hz main-thread workload, and the baseline the render-path comparison will be measured against — a ~1.5 second shot is roughly 90 frames and sends the background thread exactly **one** message, at quiescence. The physics is split one worklet per phase rather than inlined into a single body, which works because a captured `'main thread'` worklet resolves to a real callable on the other side (a captured plain function does not — hence the tuning constants being inlined, with a test pinning them against `tuning.ts`). Because `'main thread'` is just a string expression statement under node, the tests drive the **real** worklets rather than a copy.

### Changed

- **BREAKING — `@sigx/lynx-list`: `itemSnap` takes the shape native actually reads** (#950). It was typed `'start' | 'center' | 'end' | 'none'` and emitted as a bare string, but **both platforms read `item-snap` as a dictionary** — `setPagingAlignment(ReadableMap)` on Android, `LYNX_PROP_SETTER("item-snap", …, NSDictionary *)` on iOS — so the string never reached either setter and paginated snapping has never worked. It went unnoticed because the prop has no consumer anywhere in the repo: no package, no example, and the one test asserted only that the string landed as an attribute. `itemSnap` now accepts either the alignment shorthand (`'start' | 'center' | 'end'`, expanded to `factor` `0` / `0.5` / `1`) or the full `{ factor, offset, maxSnapCount }`, and is normalized to the dictionary before emission. `'none'` is gone — omit the prop, which is what native means by an absent `item-snap`. Also adds **`maxSnapCount`** (Lynx 4.0+): how many items one fling may cross, default `1`, emitted only when set so pre-4.0 hosts see the attribute unchanged.

- **`@sigx/lynx-plugin`: `enableElementApiNewRegistration` page-config flag** (#957). Lynx 4.0 can register the Fiber Element API through a new raw binding path instead of the long-standing `RenderBindingFunction` one. Pinned **off** — the path every `<sigx-*>` custom element is verified on, since they are all created through the generic `__CreateElement` and therefore move as one surface. This one is encoded for a stronger reason than the other flags: upstream marks it `readSettings: true`, so a **host setting** can flip it under a bundle that never asked for it; the page config takes precedence, so writing the resolved boolean keeps the choice with the app. Opt in with `pluginSigxLynx({ enableElementApiNewRegistration: true })`.

  Four other 4.0 page-config flags were evaluated and deliberately left alone, with the reasoning now in the plugin README: `enableNativeInteraction` (belongs with the gesture work), `syncXElementRegistry` (no evidence it helps), `enableNativeList` (device-tested in #950 — it does not do what it looks like it does, because `custom-list-name` still selects the platform node), and `enableSingleSession` (a devtool setting, not a page config).

- **`@sigx/lynx-plugin`: `enableNewSticky` page-config flag** (#950). Lynx 4.0 ships a new sticky layout implementation for `<list>` section headers, gated behind this page config and **off by default upstream**. The plugin now encodes the resolved boolean rather than leaving the key absent, so an engine that later flips its own default cannot relayout our sticky headers without us choosing it. Opt in with `pluginSigxLynx({ enableNewSticky: true })`; hosts older than 4.0 ignore the key.

- **BREAKING — the native Lynx engine moves from 3.9.0 to 4.0.1** (#946). `@sigx/lynx-cli`'s Android and iOS templates now pin `4.0.1` for `lynx`, `lynx-jssdk`, `lynx-trace`, `lynx-service-{image,log,http}`, `xelement`, `xelement-input` and `lynx-processor` (Gradle) and `Lynx`, `LynxService`, `XElement` (CocoaPods), with `@sigx/lynx-dev-client`'s devtool coordinates and `@sigx/lynx-icons`' `xelement-svg` following. **PrimJS is now pinned explicitly at `4.0.0` on both platforms** — the old comments claiming an explicit pin would mismatch the engine described 3.9, which wanted the pre-release `3.8.0-alpha.6`; Lynx 4.0.1 declares stable `primjs 4.0.0` in its POM and `PrimJS/quickjs == 4.0.0` in its podspec, so the pin now states the pairing instead of hiding it. The JS side gains a `@lynx-js/*` block in the pnpm catalog — these deps were spread over nine manifests at four different range styles, which resolved eight of them to two versions at once — and `@lynx-js/types` moves to the `4.0.x` line.

  **Breaking:** apps must rebuild their native hosts (`sigx prebuild --clean`) and cut a store release. The Lynx SDK version is folded into the OTA runtime-version fingerprint, so **every already-published OTA update is invalidated by this bump**: a 4.0.1 binary will not accept a bundle published against a 3.9.0 host, and a 3.9.0 binary still in the field will not accept anything published after it. Publish fresh updates once the new binary ships.

  What it unlocks, all still to be adopted: real CSS media queries with a dynamic `UpdateColorScheme` API, element templates with event/data attributes and cached static trees, a native `<blur-view>` (including iOS liquid glass), first-party `<webview>` and `<markdown>` elements, memory and frame metrics, declarative pan interception, and `default-value` on inputs. Two upstream behaviour changes ship on by default and are worth knowing about: text render optimization (iOS `enableTextLayerRenderer` flips to on) and animation culling for offscreen views. Two others are page-config-gated and default **off**, so nothing changes until we opt in: `enableNewSticky` and `enableElementApiNewRegistration`. What 4.0 does *not* bring: the gesture arena still reserves `PINCH`/`ROTATION` enum slots without shipping handlers for them (verified against the 4.0.1 handler factory), so `<sigx-pinch>` stays.

- **BREAKING — `@sigx/lynx-secure-storage`: `set`/`get`/`delete` are now `setItem`/`getItem`/`removeItem`** (#903, #907). The two storage packages contradicted each other about the same operation: `@sigx/lynx-storage` used `setItem`/`getItem`/`removeItem`, this one used `set`/`get`/`delete`, and callers swap between them by durability. `setItem` wins because it matches `localStorage`, `@react-native-async-storage/async-storage` **and** `expo-secure-store` — arriving from web or React Native, it's the name you already know. No aliases: keeping both spellings alive is the thing being fixed. `clear`, `hasKey` and `isAvailable` are unchanged. Native wire names stay `set`/`get`/`delete` — they aren't public API, and renaming them would churn Swift, Kotlin and the manifest for no caller benefit.

- **BREAKING — `@sigx/lynx-clipboard`: `setString` is now `Promise<void>` and rejects on failure** (#872). It was synchronous and returned `void`, so a failed write was **silently invisible**. That wasn't theoretical: Android's `setPrimaryClip` genuinely throws for a clip over the binder transaction limit, and the native method returned nothing, so JS could never learn about it. Both native sides gained a callback; the JS unwraps it through core's `unwrapNativeVoid`, rejecting with a `SigxError` (`code: 'native_error'`). Existing `Clipboard.setString(x)` calls keep compiling, since the promise is simply unawaited — but they do **not** keep behaving the same: an ignored rejection is an unhandled rejection, which surfaces as an `unhandledrejection` event on web and which this engine has treated as fatal (see #863). So the sweep isn't optional tidying — an unawaited call that previously failed silently can now take the app down. On web the same call now rejects when the browser denies clipboard-write permission, instead of logging and swallowing it.

  Two clipboard gaps are also settled as **won't-do**, with the reasons now in the README: **URL clipboard** (iOS has a dedicated `UIPasteboard.url` slot, Android has no equivalent, so one call would mean different things per platform) and a **change listener** (iOS has no clipboard-change notification at all, and polling fires the "Pasted from …" toast repeatedly). Image support is deferred to #934.

### Added

- **`@sigx/lynx-runtime`: `useFrameCallback` — a per-frame main-thread callback** (#933). The runtime had no per-frame API at all, so anything needing one — a physics simulation, a game loop, an inertial settle, a custom easing that has to see every frame — hand-rolled a self-recursive `requestAnimationFrame` chain inside a worklet body and guarded it with a `MainThreadRef` flag (`@sigx/lynx-gestures`' `Draggable` edge-scroll tick is the in-repo example). `useFrameCallback(worklet)` registers the worklet once and returns `{ start, stop, dispose }`; the main thread drives **one** rAF chain for every registered callback and invokes each active one with `{ timestamp, timeSinceFirstFrame, timeSincePreviousFrame, frameNumber }`. `timeSincePreviousFrame` is `0` on a run's first frame and clamped non-negative, so an integrator can never be handed a negative `dt` when the wall clock steps backwards. The ctx crosses the bridge once and is hydrated once: reusing the per-call `INVOKE_WORKLET` path instead would deep-clone `_c`, rebind, and re-`addRef` every `runOnBackground` handle **sixty times a second**, climbing upstream's `_jsFunctionLifecycleManager` refcount without bound. Activation is a separate wire op precisely so it is reachable from the main thread: `startFrameCallback(fc)` / `stopFrameCallback(fc)` are themselves `'main thread'` worklets, so a fling's `onEnd` starts the simulation in the frame the finger lifts rather than a background round trip later, and the simulation stops itself the frame it settles. New wire ops `REGISTER_FRAME_CALLBACK` / `SET_FRAME_CALLBACK_ACTIVE` / `UNREGISTER_FRAME_CALLBACK`.

- **`@sigx/lynx-testing`: `waitFor`, `findBy*` queries, `within`, and failure output that prints the tree** (#908). The package had no way to wait for a *condition* — `waitForUpdate()` advances exactly one microtask plus one macrotask — so any test whose state needed more turns had to guess how many, and the guess is load- and engine-dependent. That is the root cause of both flaky tests in `@sigx/lynx-emoji` (`picker-layout` pumped five turns, `grid-scroll` slept 60ms), and 12+ test files across the repo hand-roll a timing wait today. `waitFor(condition)` polls instead, treats a throwing condition as "not yet", and on timeout rethrows the condition's own error rather than a bare timeout — so a failure still says what was missing. `findByType`/`findByText`/`findByProp` pair it with the matching query, `within(node)` scopes a query to a subtree, and a failing `getBy*` now prints the tree it searched instead of only naming what it wanted.

### Fixed

- **`@sigx/lynx-runtime-main`: animated method bindings never resolved their element on native** (#930). `flushAnimatedMethodBindings` unwrapped a bound `main-thread:ref` by reading `_el`, the handle on our own `MTElementWrapper`. On native `bindMtRef` hands the element to upstream's `updateWorkletRef`, which wraps it in `@lynx-js/react`'s own `Element`, whose handle is `element` — the same class `upstream-invoke-patch.ts` patches for #863. So every native binding fell through to the registry fallback, found nothing, and stayed dirty forever, while the identical code worked on web. Affected every `useAnimatedMethod` consumer.

- **`@sigx/lynx-runtime-main`: a natively-rejected animated method invoke is retried** (#930). The flush kept a binding dirty when the invoke *threw* or the ref was unresolved, but `__InvokeUIMethod` returns normally and reports failure through its callback — which was ignored, so `lastValue` was recorded regardless. Android creates a `<list>` platform UI asynchronously, so the first flushes answer `NO_UI_FOR_NODE` (6); those counted as delivered and never retried, stranding the native state for any producer that then settled. The callback may run synchronously (native answering inline, the ordering trap behind #863) or later, so both are handled, and a late failure for a stale attempt cannot clobber a newer value that already applied.

- **`@sigx/lynx-runtime`: a derived value can skip the background bridge** (#930). `useDerivedValue` / `useDerivedValueReactive` registered a BG sink unconditionally, so a derived value consumed only by main-thread bindings still published every fold. A gesture delta changes every frame by construction — ~60-100 MT→BG dispatches a second for a reader that does not exist, enough on its own to trip the engine's limiter (`ContextProxy::DispatchEvent called too frequently`, error 204) and red-box mid-drag. Both forms now accept `{ bridge: false }`: the value still exists and folds on the main thread, only the publish is skipped.

- **`@sigx/lynx-cli`: `run:{android,ios} --release` no longer packages a stale JS bundle — or none at all** (#960). Embedding the built bundle happened inside `runPrebuild`, *after* its fingerprint fast path. That fingerprint covers prebuild's inputs — config, manifests, templates — and deliberately not the JS bundle, so on a JS-only change the fast path fired and returned before the copy ever ran. The release build then packaged whatever the native project was already holding: the previous bundle, or on a checkout where the fast path fired before anything had been embedded, nothing at all. Nothing downstream could catch it — Gradle and Xcode saw genuinely unchanged inputs and correctly reported up-to-date — so the failure reached the device as an app that launches fine and simply **runs older code**, or one that shows "No bundle found". Embedding is a build-output copy rather than a generation step, so it no longer skips with the pipeline. Release builds additionally verify the bundle they are about to package byte-for-byte against `dist/main.lynx.bundle` and refuse to continue on a mismatch, because this is not a failure you can see: minification defeats grepping the APK for a new symbol, and comparing hashes was the only thing that ever confirmed it. Found twice while measuring on device — once as "no bundle", once as a stale one — costing a build cycle each time.

- **`@sigx/lynx-runtime-main`: a gesture registered before its element exists is no longer dropped** (#958). `useGestureDetector` pushes its registration from `onMounted`, and the element is bound by a separate op. Normally the ref op lands first — but not when the detector's owner mounts *earlier* than the element it binds to, which is what any component that measures itself before rendering its content does. The main thread resolved the element, found nothing, and gave up: the op was pushed, the batch stayed well-formed, nothing threw on either thread, and the gesture was **permanently dead with no diagnostic at all**. It now parks the registration and replays it when the element binds — from `bindMtRef`, the chokepoint both binding paths share, since elements inside a compiled snapshot template never emit a `SET_MT_REF` op at all — in arrival order — a composed gesture arrives as several ops whose relations reference each other by id, so order is load-bearing. A REMOVE arriving while the SET is still parked forgets it, so a component that unmounts inside that window doesn't install a gesture for itself a frame later. Found while building `examples/flik` (#937), where it cost a full device-debug session to identify precisely because it was invisible.

- **`@sigx/lynx-audio`: `onMeter`'s unsubscribe no longer starves other listeners** (#867). The disposer wasn't idempotent, so calling one listener's disposer twice — an ordinary double effect-cleanup — drove the shared reference count to zero and told the native side to stop metering **while another listener was still subscribed**. It went silent, with no error. Each disposer now releases at most once, per `CONVENTIONS.md` C7.
- **`@sigx/lynx-audio`: malformed native payloads say what went wrong** (#867). `getStatus()` typed its result as `PlayerStatus` without checking, handing callers `undefined` where numbers were promised; `stop()` read `.uri` off a payload checked only for `.error`, so an absent result surfaced as a `TypeError` on `undefined` rather than a message. Both now normalize, and thrown errors carry the scoped `[@sigx/lynx-audio]` prefix and a machine-readable `code`.
- **`scripts/check-module-manifests.mjs` no longer misses calls with nested generics** (#867). `callAsync<Partial<T> & { error?: string }>(…)` read as uncalled, because the generic was matched with `<[^>]*>` and stopped at the first `>` — producing false "declared but never called" drift, one of which was already sitting in the baseline for `@sigx/lynx-updates`.

- **A UI method that errors no longer red-boxes the app** (#863). A main-thread `invoke(...)` whose native answer arrives inline was escalated to a fatal main-thread exception, whatever the caller did. Reproduced in the showcase's Chat composer: each appended message makes `<List inverted stickToBottom>` issue a smooth `scrollToPosition`, the relayout that causes fires `layoutcomplete` again, and its re-pin issues a second one while the first is still animating — so native answers `{code: 1, data: "dumplicated, scrollToPositionSmoothly is working"}`, meaning nothing worse than "already scrolling". Both the upstream worklet `Element.invoke` (`@lynx-js/react`) and our own `MTElementWrapper.invoke` rejected from *inside* the Promise executor, because `__InvokeUIMethod` calls its callback synchronously; PrimJS reports unhandled rejections at rejection time, so the engine had already fired before `invoke()` even returned. No caller-side guard could win that race — `@sigx/lynx-list`, `@sigx/lynx-emoji`, `@sigx/lynx-webview` and `@sigx/lynx-gestures` all carried correct-but-inert `.catch()`es. Both implementations now settle an envelope that can only resolve and derive the caller-facing promise from it, so the rejection lands one microtask later, after callers have attached their handlers. The public contract is unchanged: resolves with `data` on `code === 0`, rejects with the same `Error` otherwise; a caller that attaches no handler still gets a genuine unhandled rejection. Since native binds `mtRef.current` to upstream's `Element`, its prototype is patched once off the first bound ref (`upstream-invoke-patch.ts`) — remove that shim if upstream defers the rejection itself.

- **`@sigx/lynx-webrtc`: Android release builds no longer abort on the first `getUserMedia`** (#854). R8 deleted `org.webrtc.WebRtcClassLoader` — a class libwebrtc's `JNI_OnLoad` looks up by name and that has no Java callers at all — so loading the native library killed the process (`SIGABRT`) the moment a call started. Debug builds are unminified, which is why this only ever showed up in store builds: a release APK carried 100 `org/webrtc` class names where the debug one had 438. The `io.github.webrtc-sdk` AAR ships no consumer proguard rules, so nothing supplied the keep. The module now declares its own.

### Added

- **`@sigx/lynx-clipboard`: a showcase screen, and tests for the path that ships** (#872). The module review found the native surface (`src/clipboard.ts`) had **no tests at all** — only the web shim was covered — and no showcase screen, so there was no way to exercise it by hand on a device. Both now exist; the screen deliberately covers the failure paths (unlinked module, empty clipboard, denied web read) rather than only the happy one. Also adds a public-surface freeze test, which additionally pins that the web and native implementations expose the same methods — the plugin swaps them by `extensionAlias`, so a method added to one and not the other is a runtime failure on whichever target missed it, invisible to a typecheck.

### Fixed

- **`@sigx/lynx-clipboard`: `getString()` / `hasString()` no longer assert their return type** (#872). `callAsync<string>` only *declares* the type; a malformed native payload — or `undefined` from a denied web clipboard read — was handed to callers as a `string` that wasn't one. Both now coalesce. Also: the web path's write failure goes through `createLogger` instead of `console.warn`, so it reaches the `sigx dev` dashboard (it is the only signal a caller gets, since `setString` is sync `void`); `sideEffects: false` is declared, which is what makes the package tree-shake; and the README documents that every method throws when the module isn't linked, plus the text-only and can't-report-failure limitations.

- **`@sigx/lynx-core`: `subscribeNative`, `unwrapNative` and `SigxError`** (#860). The three pieces every native module was reinventing. `subscribeNative(channel, cb)` is one native → JS event subscription — emitter lookup, the string-or-object payload parse, a listener-throws guard and the off-device no-op fallback, all in one place; sixteen files had each re-derived them. It returns `() => void` and is safe to call twice, per `CONVENTIONS.md` C7. `unwrapNative(pkg, action, raw)` is the single `{ error }` unwrap, replacing five bespoke variants and throwing `[@sigx/lynx-<pkg>] <action> failed: <cause>` (C4, C10). `SigxError` carries a machine-readable `code` and the raising package, for anything a caller might branch on. Existing packages adopt these through their module review issues (epic #857).
- **Two CI gates for the module contract** (#860). `pnpm check:conventions` enforces the mechanically-checkable parts of C1–C12 — no bare `isAvailable` export, no `isAvailable` returning a Promise, `PermissionResponse` re-exported by permission-bearing packages, scoped prefixes on thrown messages, a `## Web` section in every native module's README. `pnpm check:manifests` cross-checks each module's method names across JS call sites, `signalx-module.json`, the Swift `methodLookup` and Kotlin's `@LynxMethod` — nothing validated these before, and four had already drifted. Both run as ratchets against a checked-in baseline: pre-existing violations are recorded and owned by module review issues, new ones fail CI, and a baseline entry that is no longer needed also fails, so the baselines shrink as audits land.

- **`@sigx/lynx-cli`: native modules can contribute R8 keep rules** (#854). New `android.proguardRules?: string[]` field in `signalx-module.json`, aggregated across linked modules (de-duped) and written to a generated `app/proguard-rules-generated.pro` that the scaffold's `build.gradle.kts` lists in `proguardFiles(...)`. Previously a module whose native dependency shipped no `proguard.txt` had no way to say so, and the app's own `proguard-rules.pro` is scaffold-once — so the rules could not be added on the module's behalf either. That file stays hand-owned; prebuild only ever writes the generated sibling. Run `sigx prebuild` after upgrading.

- **Device rotation: in-place relayout, live screen metrics, and a runtime orientation lock** (#856). A sigx-lynx app can now rotate. Three pieces, all in `@sigx/lynx-core` plus the generated hosts:

  **It rotates in place.** The managed Android manifest now declares `configChanges="fontScale|orientation|screenSize|smallestScreenSize|screenLayout|keyboardHidden"` — a rotation used to recreate the Activity, rebuild the LynxView and reload the bundle, losing all app state. On iOS the host pinned `preferredLayoutWidth/Height` to the launch size with `layoutWidthMode = .exact` and never updated it, so the engine kept laying out portrait-shaped content in a landscape window; the new `ScreenMetricsPublisher` re-pins them and calls `updateViewport(…needLayout: true)` on every size change. Both platforms also push `LynxView.updateScreenMetrics()` so `rpx` re-bases. (`uiMode` is deliberately still absent from `configChanges` — dark-mode switching keeps going through Activity recreation, which `@sigx/lynx-appearance` is built around.)

  **Live screen metrics in JS.** `useScreen()` returns a reactive `{ width, height, scale, orientation, isLandscape }` (logical units) that follows rotation, split-screen and foldable unfold; `useOrientation()` is the coarse `'portrait' | 'landscape'` read, and `useScreenMT()` is the synchronous form for `'main thread'` worklet bodies. `Platform.pixelWidth`/`pixelHeight` remain a load-time device snapshot by design — use these wherever the value feeds layout. `readGlobalScreen()` also closes a long-standing gap (#333): it reads `__globalProps`, which is mirrored onto both threads, so screen size is finally available on the background thread where `lynx.SystemInfo` is empty. `@sigx/lynx-web-host` publishes the same two channels from `resize` / `screen.orientation`.

  **Runtime lock.** `Orientation.lock('landscape')` / `.unlock()`, plus `useOrientationLock(...)` which holds the lock for exactly as long as a screen is mounted — stacked, so popping a covering screen restores the covered one's lock instead of falling through to the build default (`@sigx/lynx-navigation` keeps covered screens mounted). `'default'` means "no runtime lock" and is an alias for `unlock()` on every platform. `signalx.config.ts`'s `orientation` is the ceiling: requesting something the app didn't declare **rejects** with a message naming the config change instead of silently doing nothing. On iOS 15 a lock applies at the next physical rotation (forcing one needs `requestGeometryUpdate`, iOS 16+); no private-API fallback.

  Consumers that had frozen their dimensions at module load now follow rotation: `@sigx/lynx-sheet`'s detents and bottom-edge anchor (closes #791), `@sigx/lynx-navigation`'s transition geometry and edge-back threshold, and `@sigx/lynx-daisyui`'s `<Select>` dropdown placement. Run `sigx prebuild` after upgrading — AndroidManifest / App.swift / ContentView are managed files.


## [0.26.0] - 2026-08-05

### Added

- **`@sigx/lynx-list`: `bottomInset` — frame-synced bottom content inset (Android + iOS)** (#844). New prop `bottomInset?: number | SharedValue<number>`: the native recycler keeps that much of its bottom viewport clear, applied directly (no CSS write, no layout pass) so a main-thread SharedValue — `useKeyboardLiftSV()`, a `BottomSheet`'s `onReveal` — can drive it per frame. The package gains its first native side under the opt-in platform tag `sigx-list` (via `custom-list-name`, set only when the prop is present): Android `SigxListUI extends UIList` (RecyclerView padding delta + pinned `scrollBy` compensation, re-stacked across CSS relayouts); iOS `SigxListUI: LynxUICollection` (`contentInset.bottom` delta with delta-measured pinned compensation, re-stacked in `updateFrame`, plus an `alignTo:"bottom"` bias in `scrollToPosition` — the engine scroller targets the viewport bottom ignoring extra inset, which would land every chat re-pin under the keyboard). In chat mode the newest item stays anchored above the inset via same-frame native compensation, and chat release detection becomes inset-aware (tracked on the main thread as `scrollTop + inset`) so compensation scrolls can't falsely release the pin or fire spurious `endReached`. Run `sigx prebuild` after upgrading; hosts without the native module (web) ignore the inset.

- **`@sigx/lynx-navigation`: `useDidAppear()` — run work after the entrance transition settles** (#849). The heavy-work sibling of `useFocusEffect`: the callback runs only once the screen is focused *and* no transition is in flight, with the returned cleanup on blur, on a new transition, or on unmount. `useFocusEffect` cannot serve this case — `useIsFocused` is `nav.current.key === myKey` and a push commits the stack immediately, so it fires while the slide is still running. That matters because component setup runs on the BG thread but the resulting op batch is applied on the MAIN thread in one uninterruptible pass — the same thread driving the tween — so mount work scheduled on focus starves the animation.

- **`@sigx/lynx-runtime`: `useAnimatedMethod` — SharedValue-driven native UI methods** (#844, groundwork). The imperative sibling of `useAnimatedStyle`: bind a `MainThreadRef`'s element to a `SharedValue` and the MT runtime invokes a named UI method (`{...params, [valueKey]: value}`) on every flush boundary where the value changed — same dirty-diffing and derived-value ordering as style bindings, no thread crossing per frame. For natively-backed per-frame state a style write can't express without a layout pass; first consumer is `<list>`'s upcoming `setBottomInset` (frame-synced bottom inset under keyboards and dragged sheets). Static and reactive (`() => spec | null`) call shapes; new wire ops `REGISTER_AV_METHOD_BINDING` / `UNREGISTER_AV_METHOD_BINDING`.

### Fixed

- **`@sigx/lynx-navigation`: a modal/sheet pop now slides immediately** (#849). Every pop awaited `settleBeforeTransition()`, which exists to let the *un-hidden* underneath layer relayout before the slide starts. Only a card pop un-hides anything — `computeLayers` keeps the whole static run below an overlay at `hidden: false` the entire time it is up — so for a modal or sheet that wait staged nothing and simply delayed the motion. On a heavy screen `pendingOps()` never goes quiet, so it cost the full `PRE_STAGE_MAX_MS`: the header repainted instantly and the screen then sat still. Measured on device, popping the showcase's Chat composer produced 2-3 frames in the 400 ms after the press; it now produces 35-36, matching a light screen.

- **`@sigx/lynx-navigation`: navigation requested mid-transition is replayed instead of dropped** (#849). `push` / `replace` / `pop` used to `return` outright while a transition was in flight. A transition outlives its own slide — `animateProgress` awaits a main-thread landing ack after the duration elapses — so a press arriving once the animation *looked* finished still vanished, and (since consumers commonly fire a selection haptic first) the dead tap even buzzed. The most recent intent is now remembered and replayed when the transition clears, guarded so it can't over-navigate: a repeated tap on the same row won't stack a duplicate screen, a second back press won't pop an extra one, and an intent older than 1 s is discarded. Gesture starts (`beginBackGesture`, `commitSheetDismiss`) and programmatic jumps (`popTo`, `popToRoot`, `dismiss`) are still dropped, where a late replay would be more surprising than a no-op.

- **`@sigx/lynx-emoji`: category slices are bucketed in one pass** (#849). Building the picker ran one `filter` per category over the whole ~1,900-entry dataset — nine full walks. Now a single pass buckets every entry into its category.

- **The `sigx dev` dashboard is laid out from the pane the shell gives it, and shows the QR once** (#824). `@sigx/lynx-cli` moves to `@sigx/cli ^0.9.0` and `@sigx/terminal ^0.11.0`, and its plugin manifest declares `"requires": ">=0.9.0"` (was `>=0.4.0`).

  The version floor matters twice over. `@sigx/cli` 0.9.0 pins `@sigx/terminal ^0.11.0` while this package pinned `^0.10.0` — disjoint single-minor ranges, so pnpm resolved **two physical copies** of `@sigx/terminal`, and with them two `@sigx/reactivity` and two `@sigx/runtime-terminal` singletons. A renderer singleton is exactly the wrong thing to have two of: `printStatic` from one copy knows nothing about the live region the other mounted. And `ShellTab.render(pane)` is a *host* capability — the installed `sigx` binary is what calls it, so on a 0.8.x host `render()` receives no argument and every `pane.height` would be a `TypeError` at first paint.

  `requires` does **not** prevent that second case. `@sigx/cli`'s plugin discovery treats the field as advisory: it logs `… requires sigx CLI >=0.9.0 but this project runs 0.8.0 — some commands may misbehave` and then loads the plugin anyway (verified against a real 0.8.0 binary, which registers every command after the warning). So the manifest floor is a diagnostic, and the actual gate is `supportsShellPane(ctx.cliVersion)`: on a host that cannot pass a pane, `sigx dev` prints an actionable warning and falls back to the plain streaming banner — the same fully-working output `--no-ui` produces — rather than crashing. Unknown or unparseable versions count as unsupported, because the cost is asymmetric: a false negative is the plain banner, a false positive is a stack trace.

  With the pane available, `Math.max(8, getTerminalSize().rows - 13)` is gone — a literal that re-counted the shell's own chrome by hand and was wrong the moment the shell changed shape, silently. All arithmetic now lives in `src/dev-ui/layout.ts` and is derived through `boxChrome`, which mirrors the renderer's `drawBox`, so a change to the box primitive moves these numbers instead of invalidating them. One asymmetry is worth knowing, because it is invisible until it shears the screen: `LogView` takes its *outer* width and subtracts its own box internally, while `DataTable` charges the cursor gutter and its box against the terminal only when deriving its **default** width — an explicit `width` goes straight to `layoutTable` and the gutter is still prefixed to every row. Handing `DataTable` the raw pane therefore overflows by exactly one column. `dataTableWidth()` exists to stop that being rediscovered.

### Added

- **Device logs keep their structure, and the dashboard can filter them** (#828). Every device log already reached the CLI as a record — level, platform, client id, timestamp — and `formatDeviceLogLine` flattened it to an ANSI string one line later (`dev-server.ts`). Nothing downstream could filter by anything, and no amount of work on the dashboard could recover it, because the structure was gone before the dashboard saw it.

  A new structured store keeps the records, and the old `Logs` tab splits in two: **Build** keeps the text `LogView` over the dev server's and native toolchain's output, which is genuinely unstructured and right to leave as text, and **Logs** becomes a `DataTable` of your app's `console.*` — time, level, device, namespace, message — with per-level colouring and a cursor.

  One dimension came free. `@sigx/lynx-core`'s default transport emits `[${namespace}]` as the first console argument, so a `createLogger('http')` record is machine-identifiable: namespace is a column and a filter, matching the namespaces `signalx.config.ts` can already silence. Only an *exact* `[…]` first argument counts — `console.log('[warn] hand-rolled')` is one argument, not a namespaced record, and inventing a namespace nobody declared would be worse than showing none.

  Filters are slash commands, and their shape is dictated by the host: `runShell` dispatches on the first token and discards the rest, so a slash command cannot take an argument. Hence one command per level (`/level:warn`, `/level:error`, …, `/level:all`) — the palette filters by prefix, so typing `/level` lists them all with descriptions, which is more discoverable than an argument would have been. Values only known at runtime cycle instead: `/platform` and `/ns` step through what has actually been seen, `/filters` clears everything, `/clear` discards the collected logs, and the `l` key cycles the level floor. **A free-text search is not expressible under this contract** and is left out rather than faked.

  While a filter is active the status bar carries the withheld count, because a filtered view that looks quiet is otherwise indistinguishable from a quiet app. A multi-line message shows a `⏎n` marker and expands with `Enter` into a detail pane (Esc closes) — below 20 rows the detail takes the pane rather than sharing it, since a split leaves the table too short to be worth having.

  Two deliberate routing decisions. Device logs no longer go into the text store at all, so device chatter cannot drown the build log — that separation is half the point of the split. The exception is `error`, which is *also* written to the permanent transcript: in fullscreen that flushes to real scrollback on exit, so a crash trail survives the alt screen and stays greppable. Doing that for every level would dump the whole session into the terminal on quit. `--no-ui`, non-TTY, and `--no-device-logs` are all unchanged.

  Retention is 2 000 records, not the text store's 10 000: each record holds the full message plus derived fields and the filter is a scan, so this is the interactive working set — the full history is still scrollable in **Build**. The filtered view is memoised against a monotonic buffer version rather than the record count, because at the retention limit every push evicts one and appends one — the count is constant while the contents turn over completely, which would have frozen the view exactly when logs were busiest.

The slot is now declared as what it has always been (`Define.Slot<'default', { active: boolean }>`) and invoked with the context, so the declaration and the runtime agree and `active` is type-checked at the call site instead of cast. The manual normalise is kept: a nested function, or a single-element array holding one, still has to be applied by hand, and plain JSX children pass through with `active` ignored.

## [0.22.0] - 2026-07-28

### Fixed

- **`@sigx/lynx-sheet` — a `{ keyboard: true }` detent no longer double-counts the bottom inset** (#811). `resolveDetents` added the bottom safe-area inset back onto keyboard detents unconditionally, but that add-back is only correct for a sheet whose bottom edge reaches the true screen bottom. A sheet that also passes `bottomOffset` (an ancestor `SafeAreaView` already pads the gesture bar — the showcase composer's case) counted it twice and opened a gesture bar **taller than the keyboard it replaces**: 73 px on a Pixel 9 Pro XL, visible as the composer's input row jumping on every keyboard↔emoji swap. Worse, that inflated detent is also `setReveal`'s `openFloor`, which clamped away the live main-thread capture — so `openToLift`, whose whole purpose is a pixel-stable swap, was a no-op. It now adds back only the part the sheet still has to cover: `max(0, bottomInset - bottomOffset)`. Sheets that don't pass `bottomOffset` are unchanged.
- **`@sigx/lynx-keyboard` — the observed keyboard height is now remembered app-wide and across runs** (#811). The memory keeps the LATEST height, never a running max: a device's keyboard is not one height (the suggestion strip comes and goes, numeric and alpha layouts differ, IMEs differ), and a panel sized to occupy its space must match the keyboard about to appear — the best predictor being the one that appeared last. Keeping a max latched onto the tallest ever observed and opened the panel 36 px too tall from then on. It was tracked per `<BottomSheet>` instance starting from 0, so the first keyboard-sized panel opened on a screen where nothing had been typed yet fell back to `fallbackPx` and then visibly corrected itself when the real keyboard returned — the showcase composer's input row jumped **53 px** on that first emoji→keyboard swap (measured: panel at 64+320 dp, real keyboard 64+344). `rememberedKeyboardLift()` exposes the last lift seen, recorded by any mounted lift hook and persisted via the optional `@sigx/lynx-storage` peer (without it the memory is per-run); `<BottomSheet>` seeds from it. A real observation supersedes a restored one even if shorter, so a different IME or split screen can't strand a panel too tall. Down to **1 px** on the same swap, across a full app restart with no keyboard shown in that run.
- **`@sigx/lynx-sheet` — an already-open sheet now follows a change to its open detent** (#815). `<BottomSheet>` only moved on an `open` *transition*, so changing `openDetentIndex` (or re-resolving `detents` such that that index moves) while the sheet was already open did nothing: it kept the height it opened to and the new content rendered into the old slice. That is the natural shape for a sheet hosting more than one panel — a keyboard-height panel and a taller one, swapped without ever closing — and the only workaround was to close the sheet and reopen it a tick later, throwing the reveal away and flashing. Detent *identity* changes were already live (#743); the open target was the remaining gap. Two guards keep it from fighting the user: nothing happens mid-drag, or once the sheet has been dragged off the position `open` put it at. Unlike every other programmatic move here this one animates — `animate` defaults to `false` so that some *other* motion (a keyboard sliding away) can reveal an already-painted sheet, and a mid-open detent change has no such external motion.
- **`@sigx/lynx-icons-lucide` — icons containing `<line>`, `<polyline>` or `<polygon>` render again**. Lynx's `<svg content=…>` silently drops those primitives, so `hash` painted nothing at all and `smile` lost its eyes; 98 of lucide's 1,956 icons contain at least one. All three convert losslessly to `<path>`, which does paint.

### Added

- **`@sigx/lynx-sheet` — `pinnedBottomRef` and the `rest` event** (#811). The panel is laid out as tall as the top detent and slid down, so its own bottom edge is off-screen at every rest below the top detent — `position: absolute; bottom: 0` pins to a place nobody can see. `pinnedBottomRef` binds an element to the inverse of that slide, so it sits last in flow yet paints flush with the visible bottom edge, on the main thread, every frame of a drag or keyboard lift (WhatsApp's emoji category row). Cells default to the SAME screen-adaptive, text-size-aware size `<EmojiPicker>` resolves, so a strip and a grid on one surface read as one control.

### Changed

## [0.19.0] - 2026-07-23

### Changed (breaking)

- **`@sigx/lynx-sheet` — NEW package: the unified bottom sheet** (#774). One engine (`useSheetEngine` + `createSheetPan` + `Backdrop`) now powers every sheet in the framework, and a standalone **`<BottomSheet>`** ships for route-free use — the one-off tray and the WhatsApp-style composer no longer need a navigator. Geometry is declared as **`DetentSpec`s** (`px | { px } | { fraction } | { keyboard: true, fallbackPx? }`) resolved live against screen height, safe-area insets, the remembered keyboard height (the component owns the BG-reactive tracking and bottom-inset add-back apps used to hand-roll), and `topOffset`/`bottomOffset` caps so a fully-open sheet never slides under a header — `bottomOffset` matters whenever an ancestor pads the bottom safe area, since the cap anchors at the sheet's real bottom edge. Modes: persistent floor (composer) or `dismissible` (release projecting below half the floor parks at 0 + emits `dismiss`); optional `backdrop` (dim tracks the drag, inert while parked, `[0, top]` fade for dismissible sheets); `dragMode: 'handle' | 'surface' | 'grabber' | 'none'` with the full 8-step drag↔scroll arbitration in `'surface'` (this component provides the `ScrollDragHost` an inner gestures `<ScrollView>` adopts). Worklet-visible render state (drag gate, dismissible flag, bottom edge) travels a `syncGeom` push — fixing the #758 class where render-side `SharedValue` writes were silent no-ops and `dragEnabled` changes never reached the gesture.
- `@sigx/lynx-navigation` — **`presentation: 'sheet'` rebuilt on the `@sigx/lynx-sheet` engine** (#784): the navigator's sheet SV now carries **reveal px** (was progress 0..1), `SheetDragController` and `internal/sheet-math.ts` are deleted in favor of a ~40-line `SheetDragAdapter`, and `useSheetHeight()` returns the reveal SV directly. **Renamed screen options** (compile-error migration): `snapPoints` (fractions) → `detents` (`DetentSpec[]`, default `[{ fraction: 0.5 }]`), `initialSnapIndex` → `initialDetentIndex`, `dragHandle` → `dragMode`. The **inline `BottomSheet` export is removed** — import it from `@sigx/lynx-sheet` (richer API, same tuned behaviors; the release snap now uses the unified 0.2s projection). - `@sigx/lynx-emoji` — **`SheetPicker` removed** (#788): its role is exactly `<BottomSheet dismissible backdrop>` + `<EmojiPicker>`. `@sigx/lynx-daisyui`'s `EmojiPickerSheet` keeps its one-liner API unchanged, rebuilt on the unified sheet (drag-to-dismiss on a visible grabber pill, live dim, cold-mounted grid preserved); daisyui gains `@sigx/lynx-sheet` as an optional peer.

### Changed

- **Themes and safe-area insets now ride inline CSS custom properties — first-frame-perfect for runtime/backend themes** (#116). Upstream Lynx supports registering custom properties declared in inline `style` behind the `enableCSSInlineVariables` page-config flag (since 3.6; value-change propagation to descendant `var()` uses since 3.9). `@sigx/lynx-plugin` now encodes the flag into every template (kill switch: `pluginSigxLynx({ enableCSSInlineVariables: false })`), `@sigx/lynx-cli`'s native templates move from Lynx 3.8.0 to **3.9.0** (PrimJS now resolves transitively — the engine pins its exact build), and `@sigx/lynx-runtime` exempts `--*` keys from number→px normalization. On this base, `@sigx/lynx-zero`'s `ThemeProvider` declares the full theme (colors, radius/size overrides, `fontScale` text ramp) inline on its host view — **runtime-registered themes (`registerTheme`) paint their exact palette on the very first frame**, instead of a built-in fallback class swapped post-mount — and `SafeAreaProvider` declares `--sat`/`--sar`/`--sab`/`--sal`/`--safe-area-keyboard` the same way (no more `getElementById().setProperty` retry loop). ### Added

- `@sigx/lynx-richtext` — **`<sigx-richtext>` now works on web.** The rich-text input was a native-only element (UITextView / EditText) with no web counterpart, so on `sigx run:web` / `build:web` it was an inert `HTMLUnknownElement` — `MarkdownEditor` and the WhatsApp/chat composer rendered but their text field couldn't be focused or typed into (#771). - **Apps now honor the OS font scale** (#766) — text in sigx-lynx apps was rendering at unscaled CSS px, visibly smaller than every other app on a device with a non-default system text size (iOS pinned `builder.fontScale = 1.0`; Android never set it). The native hosts now seed `LynxViewBuilder.fontScale` from the OS (iOS Dynamic Type via `UIFontMetrics(.body)` — tracks Apple's real non-linear curve including accessibility sizes; Android `Configuration.fontScale`) and push runtime changes in place via `LynxView.updateFontScale()` — the engine relayouts live (no Activity recreation, no bundle reload; the managed manifest adds `android:configChanges="fontScale"`) and scales `font-size`/`line-height` only, leaving layout lengths untouched. A new `FontScalePublisher` in `@sigx/lynx-core` owns the mapping/clamping and seeds `lynx.__globalProps.fontScale = { scale, os }` before first paint; `@sigx/lynx-appearance` adds `useFontScale()` / `useFontScaleMT()` riding the engine's own `onFontScaleChanged` event. App policy via `signalx.config.ts` `fontScale: { follow, min, max }` (default `{ true, 0.5, 2.0 }` — 2.0 is Android's slider ceiling; raise `max` for text-heavy apps, `follow: false` restores the old pinned behavior). `@sigx/lynx-zero`'s ThemeProvider `fontScale` stays an independent in-app multiplier — the engine already scales its px ramp, so the two compose multiplicatively (don't seed one from the other). Module manifests may now declare `publisherClass` as an **array** (`@sigx/lynx-cli`); existing projects pick everything up on the next `sigx prebuild`. Web builds are unaffected (`@lynx-js/web-core` has no font-scale concept — tracked separately).

- `@sigx/lynx-daisyui` — plain-prop change callbacks for the two model-only form controls: `Select` gains `onChange(value)` and `Radio.Item` gains `onSelect(value)`. Both are plain function props rather than `emit` events, which is what makes them work at all — these components take a prop named `value`, and that shadows `@sigx/runtime-core`'s emit handler lookup so events never fire (#323). For controlled, non-`model` usage; `model` remains the canonical path and is written *before* the callback runs, so a callback reading the bound signal sees the committed value and the two compose. `Radio.Item` never fires while `disabled` (#336).

- `@sigx/lynx-datetime-picker` — **`formatDate(date, pattern)`**, a locale-free token formatter for displaying a picked date. The Lynx runtime ships no `Intl`, so every consumer was hand-rolling the same `pad()` + template literal (the showcase demo included); `formatDate(r.value, 'YYYY-MM-DD HH:mm')` replaces it. Tokens `YYYY`/`YY`, `MM`/`M`, `DD`/`D`, `HH`/`H`, `hh`/`h`, `mm`/`m`, `ss`/`s`, `A`/`a` in local time, `[bracketed]` literals pass through unsubstituted, and a missing or Invalid `Date` returns `''` so a cancelled result needs no null check. No month/weekday names — those need locale data the runtime doesn't have (#255).

### Fixed

- `@sigx/lynx-runtime-main` / `@sigx/lynx-web-host` — **interactive elements inside a bottom sheet now work on web** (#764). The web gesture recognizer captured the pointer on every `pointerdown`; since `pointerdown` bubbles child → ancestor, a sheet's full-surface drag captured last and retargeted the whole `pointermove`/`pointerup`/`click` sequence to itself — so a button or a suggestion-popup row *inside* the sheet never saw its own terminal event, its tap never resolved, and (for a `Pressable`) its pressed visual stranded. The composer's **send button** and **mention-popup selection** were both dead on web. Capture is now taken **lazily** — only once a drag/pinch actually commits (`Pan` onStart, pinch/rotation pair formation), never on `pointerdown` — so a not-yet-moved press leaves the descendant under the pointer to resolve its own tap, matching the native arena where an ancestor pan only wins after crossing threshold (sheet drag, draggable, swiper all verified unaffected). Alongside it, `@sigx/lynx-web-host` now honors **`ignore-focus`** on web: a capture-phase `mousedown` `preventDefault` on a non-focusable `[ignore-focus]` element keeps a tap from blurring a focused editor (so the mention trigger session survives the tap); a focusable descendant — the editor lives inside the composer's `ignore-focus` row — is left alone. Opt out with `installSigxWebHost(view, { ignoreFocus: false })`. (Touch focus management is a follow-up; the mousedown path covers mouse/desktop.)
- `@sigx/lynx-icons` / `@sigx/lynx-emoji` — **icons and the emoji picker are now consistent under the OS font scale** (#776). Font-mode `<Icon>` glyphs (FontAwesome's default) were scaled by the engine while their box stayed fixed — clipping at 1.3×+ — and SVG-mode icons didn't scale at all; the emoji picker's glyphs scaled while its pinned row geometry didn't (clipping + scroll-offset drift). Now: **icons hold their designed dp size by default** on every backend (font-mode glyphs counter-divide by the effective scale so the engine's multiply lands back on `size`), and a new **`scaleWithText`** prop on `<Icon>` (forwarded by `LucideIcon`/`Fa*Icon`) opts an icon into growing with the text — glyph and box together, live. The emoji picker is pinned end-to-end like a keyboard panel (grid cells, section labels, category tabs, tone popover; the est==actual geometry contract holds by construction — the vnode cache keys on the scale so live setting changes re-pin). Emoji inside message text are ordinary text and keep scaling with it.

- `@sigx/lynx-richtext` / `@sigx/lynx-markdown` — **the editor's text rendered ~2.25× the requested size on Android** (#770), a regression from the Lynx 3.8 → 3.9 native bump (#757): CSS-named custom-element props now ride the engine's style pipeline, which delivers `font-size` in physical px on the mount pass but the raw number on updates (both probed on device) — `COMPLEX_UNIT_DIP` then re-multiplied the mount value by density. No single native unit interpretation can satisfy both paths, so the element attribute is renamed to the non-CSS **`editor-font-size`**, which bypasses the style pipeline and arrives verbatim (dp) on mount and update alike; `RichTextInput`'s JS `fontSize` prop is unchanged. `min-height`/`max-height` arrive as layout dp consistently and were already correct; iOS was unaffected (pt) and gets the same rename for parity. On top of the unit fix, **`MarkdownEditor` now follows the OS font scale** (#766 never reached custom native text elements): `fontSize` is multiplied by the effective scale at the point the auto-grow window derives from it, so text and the 1→N-line box scale together, live. The reactive read moved to its natural home — `useFontScale()` / `useFontScaleMT()` / `readGlobalFontScale()` now live in `@sigx/lynx-core` (which owns the FontScalePublisher), are re-exported by the `@sigx/lynx` umbrella and `@sigx/lynx-appearance` (same import paths as before, no provider needed), and `AppearanceProvider` no longer carries a font-scale signal.

- `@sigx/lynx-runtime-main` — **every `Pressable`-based control was inert on web**: taps fired `longPress` instead of `press`, so nothing bound to `onPress` ever ran. `<Pressable longPressDuration={0}>` disables long-press by pushing the recognizer's `minDuration` to `Number.MAX_SAFE_INTEGER` — a delay no timer should ever reach. That's true of a native timer, but `setTimeout` coerces its delay to a signed 32-bit int, so on web it wrapped to ≤ 0 and LongPress fired on the tick *after* touch-down. The fired long-press then both disqualified the tap (`isTap` requires no long-press fired) and short-circuited `LongPress.onEnd`'s press fallback, leaving no path to `press` at all. The web recognizer now refuses to arm a timer it can't represent — a duration past the 32-bit ceiling means "never fires", as intended. `longPressDuration={0}` is what essentially every daisyui/heroui control passes (`Button`, `Checkbox`, `Toggle`, `Radio`, `Select`, `Rating`, `Collapse`, `Tabs`, `NavTabBar`) including **`NavHeader`'s back button** — so on web the whole component layer, and going back, silently did nothing (#763).

- `@sigx/lynx-web-host` / `@sigx/lynx-cli` — **navigation geometry on web now matches the `<lynx-view>`, not the monitor.** Upstream `@lynx-js/web-core` fills `SystemInfo.pixelWidth/pixelHeight` from `screen.availWidth/availHeight × devicePixelRatio` — the physical display — but everything downstream reads those as "the screen the app occupies": `@sigx/lynx-navigation` slides cards in from `SCREEN_WIDTH` px away and rests sheets at a fraction of `SCREEN_HEIGHT`, `@sigx/lynx-gestures`' Swiper falls back to it for page width, and `Platform.isPad` derives from it. In a 500×813 view on a 1710×1008 display, a sheet declaring `snapPoints: [0.4, 0.9]` settled at `translateY(604.8)` instead of `487.8` — 117px too low, and entirely below the fold on a shorter window, which is what "the sheet never appears" was. Both the generated host page (`sigx run:web` / `build:web`, via an inline `browser-config` attribute set during parsing, before the engine upgrades the element) and `installSigxWebHost` now describe the element's own box. New export `viewportBrowserConfig(view)` for hand-written host pages; opt out with `installSigxWebHost(view, { viewport: false })`. Resizes aren't tracked — web-core freezes `SystemInfo` when the view is constructed (#759).

- `@sigx/lynx-navigation` — a push/pop transition now **asserts its end state** instead of assuming the tween finished on time. The completion callback waits a BG-side wall clock, not the tween's real completion, and then clears the transition — which flips `props.animation` to `null` and unregisters the layer's main-thread binding, after which nothing ever writes the resting value. A tween that was starved, late, or never ticked therefore froze its layer at whatever transform it had reached, permanently: a `presentation: 'modal'` screen resting 44–77pt low on iOS, or a popped-to screen stranded off-screen left, which reads as "the back button does nothing". The navigator now cancels the animation and lands the target value on the main thread before the binding goes away — idempotent, so a tween that did finish writes the value it already holds (#758, shipped in #760).

- `@sigx/lynx-navigation` — the #651 pre-stage settle window is **bounded for real**. `PRE_STAGE_MAX_MS` gated only the loop condition; `await waitForFlush()` itself was unbounded, and that promise settles only when the host invokes the `callLepusMethod` callback for the batch. One dropped ack left `pendingOps()` true forever and the await never resumed — so the transition never started (the incoming screen stayed parked at its pre-stage transform) *and* the transition signal was never cleared, which made `isTransitioning()` reject every subsequent push and pop for the rest of the session. Each wait now races the remaining budget, so a lost ack costs the pre-stage, not the navigator (#759).

- `@sigx/lynx-cli` — `sigx prebuild`'s fast path now hashes the CLI's own `templates/` tree (fingerprint format `v8`). ## [0.18.1] - 2026-07-21

### Fixed

- `@sigx/lynx-navigation` — **push/pop transitions no longer stutter into heavy screens** (#651): animated transitions now *pre-stage* the incoming work. A push commits its render immediately but parks the incoming layer off-screen (the transition SV is seeded 0 in-stream, in the same MT batch as the mount and binding registrations, so no stale-SV flash) and holds the `withTiming` start until the BG→MT pipeline goes quiet — the screen's mount batch, post-mount effect flushes, native layout, and `<list>` initial cell pulls all complete while the outgoing screen is still presented, then the slide animates a fully-built tree. Cards/modals park with a ~2px sliver on-screen (`PRE_STAGE_PEEK`) rather than exactly off-screen — a fully off-screen layer's texture is culled and never rasterized, which put the whole screen's raster cost on the first animation frame (one ~36ms frame at motion onset on the 2000-row snapshot-list bench); the sliver forces the raster into the settle window, flattening the entire slide to vsync cadence. Pops get the same settle window for the underneath layer's `display: none → flex` reveal relayout. The wait is bounded (`PRE_STAGE_MAX_MS`, 160 ms), so screens that never go quiet (pollers, streaming data) still transition promptly with a best-effort pre-stage; a `reset()` during the window is guarded like the existing sheet-push deferral. `@sigx/lynx-runtime` adds the quiescence probe this rides on: `pendingOps()` — true while ops are buffered, scheduled, or sent-but-unacked; false once the MT has applied everything (pairs with `waitForFlush()`).

- `@sigx/lynx-navigation` — `<BottomSheet>` now tracks `detents` / `maxHeight` **after mount**. They were snapshotted at setup and baked into main-thread state (the `reveal` seed, both derived-value offsets, and the `minReveal`/`maxReveal`/`detents` lexicals captured by the pan worklets), so later updates did nothing — silently. That broke the component's headline use case: a composer accessory's collapsed floor is inherently variable (an attachment chip row appears above the input, the input grows from one line to several, banners come and go), and since the sheet reveals the top `reveal` px of top-aligned content, a floor that couldn't grow pushed the input row and send button out of the revealed slice and behind the keyboard. Geometry is now read live, the two derived offsets use `useDerivedValueReactive` (the derived SV identity is stable, so `onReveal` consumers stay bound), worklet geometry is pushed through a main-thread ref so the drag clamp and release-snap candidates stay current, a parked sheet follows its floor, and geometry that shrinks pulls the held `reveal` and any captured `openToLift` rest back into range (#743).

  - **Tap events arrived with every scalar field stripped (both platforms).** `sendGlobalEvent` drops a payload's sibling scalars when it carries a nested map (#342 — the same Lynx 0.5.0 / PrimJS 3.8 regression `@sigx/lynx-http` documents), and *every* notification payload nests `data`. So `title`, `body`, `foreground`, `notificationId` and `actionIdentifier` all arrived `undefined` while `data` came through intact — which is exactly why the bug read as "the data is there but tap routing does nothing", and why nobody noticed the missing scalars. Both buses now JSON-encode each event and emit it as a single string, mirroring `HttpEventBus` / `WebRTCEventBus`; the JS shim already parsed string-form events. `getInitialNotification()` returns a JSON string for the same reason — it is the one callback in the module carrying a nested map, and nested-map marshalling over `Callback` / `LynxCallbackBlock` is unproven (the sole precedent, `FilePickerModule`, is masked by JS-side defaulting) — and `src/notifications.ts` parses it.
  - **Android: a tap on an OS-rendered notification lost the payload entirely.** FCM only calls `onMessageReceived` for a backgrounded/terminated app when the message is data-only; a message carrying a `notification` block is rendered by the OS, which never invokes it — so the module never built its tap intent, and `getInitialNotification()` came back empty on exactly the cold start deep-linking exists for. `PushActivityHook` now also treats a launch intent carrying `google.message_id` as a tap and harvests the sender's `data` keys back out of it, delegating the reserved-key filter to `RemoteMessage(Bundle).getData()` (the SDK's own, so Google's reserved set stays authoritative — the approach react-native-firebase and flutterfire use). Best-effort by nature: cold start is reliable, but the warm tap goes through an intent FCM builds and may not be delivered at all, so data-only remains the dependable path when tap routing matters.
  - **Android: data-only messages showed no tray entry.** `title` was read only from `message.notification`, so the one shape that *does* reach `onMessageReceived` in the background produced no notification at all — making the standard fix for the above (switch the sender to data-only) trade one failure for another. `title`/`body` now fall back to the `data` map.
  - **Android: warm taps never reached `onNewIntent`.** The tap intent was `getLaunchIntentForPackage()`'s ACTION_MAIN/CATEGORY_LAUNCHER intent; starting one against an existing task is treated as a launcher relaunch — the task is brought forward and the intent is never delivered, so the extras evaporated and `addNotificationResponseListener` never fired for a background-but-alive tap. The module now builds an explicit-component intent with `SINGLE_TOP | CLEAR_TOP`.
  - **Android: a config-change recreate re-delivered a drained tap.** The tap marker was never cleared from `activity.intent`, so a rotation or font-scale change re-ran `onCreate` and re-stashed a payload JS had already consumed, deep-linking a second time. The markers are now consumed, and `onCreate` ignores a recreate.
- `@sigx/lynx-notifications` — iOS: `getInitialNotification()` no longer reports a notification the user never tapped. iOS populates `launchOptions[.remoteNotification]` when a `content-available` push launches the app **in the background**, with no interaction; the hook stashed that as the initial tap, so the next manual open deep-linked off a silent push. The same branch also double-handled genuine taps (captured at launch *and* republished by `didReceive`). The launchOptions branch is gone — `didReceive` fires for every real tap including cold start, since the delegate is installed before `didFinishLaunching` returns, and is now the single source of truth (the approach RN Firebase and Expo rely on) (#619).
- `@sigx/lynx-notifications` — iOS: a cold-start tap is no longer stranded when JS calls `getInitialNotification()` early. The cold-start window closed on the first `consume` even when it returned nil, so a call landing in the gap between launch and `didReceive` — the normal path for a local notification launched from a terminated state — sent the tap to the response channel, where nothing was listening yet. The window is now keyed on whether the app has ever reached `.active` (a launch tap precedes activation; an in-session tap follows it) and `consume` is a pure one-shot drain (#619).
- `@sigx/lynx-notifications` — iOS: `actionIdentifier` now means the same thing on both platforms. iOS reported Apple's raw `UNNotificationDefaultActionIdentifier` (`"com.apple.UNNotificationDefaultActionIdentifier"`) for a standard tap while Android sent `"default"` — which `NotificationResponse` documents — so an app routing on `actionIdentifier === 'default'` worked on Android and silently never matched on iOS. The native side now maps Apple's default constant onto `'default'`; custom category action ids pass through untouched. Normalized natively rather than in the JS shim, so the raw event channels carry the same contract as the typed API. Apple's dismiss constant is mapped to `'dismiss'` for the same reason, though nothing emits it yet — iOS only delivers that action for a category registered with `.customDismissAction`, and Android sets no `deleteIntent` (#619).
- `@sigx/lynx-notifications` — iOS: nested APNs custom values are recoverable. Values were coerced with `"\(v)"`, which renders a nested object as Swift's *debug* description (`{ id = 42; }`) and a JSON `true` as `"1"`. Non-string values are now JSON-encoded, so `data.yourKey` round-trips via `JSON.parse` and booleans read as `"true"`. The wire type stays `Record<string, string>` — FCM's `data` map is string-only, so strings remain the cross-platform floor (#619).
- `@sigx/lynx-cli` + `@sigx/lynx-plugin` — dynamic `import()` now works in standalone/store builds (#599). Async chunks (`dist/static/js/async/<hash>.js`) previously loaded only in `sigx dev` (the dev server served them); release builds shipped without them and no fetcher, so every dynamic import rejected at runtime with the native `No available provider or fetcher` error — silently, since nothing warned at build time. Now: (1) release flows (`sigx run:* --release`, `sigx prebuild --embed-bundle`) mirror `dist/static/js/async/**` into the native projects (iOS `LynxAssets/` blue-folder reference — injected idempotently into existing pbxprojs on prebuild — and Android `assets/`); (2) the managed native shells register production resource fetchers (`SigxProductionResources.swift`/`.kt`) that map the runtime's root-relative chunk URLs onto those embedded assets, with an http(s) fallback for remotely-hosted chunks; (3) `@sigx/lynx-plugin` pins the production `output.assetPrefix` to `/` (only when unset) so chunk request URLs stay root-relative and map 1:1; (4) `sigx build` and the plugin's after-build hook surface every emitted async chunk, and `sigx updates:publish` refuses to publish while `dist/` contains async chunks (OTA payloads carry only `main.lynx.bundle`) unless `--allow-async-chunks` is passed for remotely-hosted setups. Existing apps pick everything up on the next `sigx prebuild`.
- `@sigx/lynx-list` — edge events (`scrolltoupper`/`scrolltolower`) now act **once per arrival** and only re-arm when a real scroll moves away from that edge. Native re-fires them continuously while a list is parked at an edge — measured 1,674 `scrolltoupper` dispatches with no scrolling at all and only 2 renders (~240/s, far above frame rate) — and a list whose container size is momentarily invalid reports both edges at once. Acting on every dispatch ping-ponged the window (expandNewer trims the head → the top edge re-fires → expandOlder trims the tail → repeat), spun hundreds of re-renders, and handed consumers hundreds of bogus `startReached` calls (#606).
- `@sigx/lynx-list` — the top edge is now bound only when it can do work (chat mode, a window with older items to reveal, or a real `onStartReached` listener), and `bindscroll` is throttled by default (100ms). `List` always binds `bindscroll` internally and nothing internal needs per-frame resolution; both changes cut needless native→JS dispatch (#606).
- `@sigx/lynx-emoji` — the picker no longer renders blank, and switching categories no longer trips the engine's event-dispatch limiter (error 204, red-screened by the dev overlay). Two independent causes, both measured on device:
  - **Blank:** the native list produces invalid layout — blank, or content displaced off-screen — once roughly 130-150+ cells are mounted at once. It is racy (the same count renders on one run and blanks on the next), it predates the windowed grid (release 0.12.2 mounted all 171 smileys and blanked identically), and it reproduces with no emoji code at all by raising the List showcase demo's window to ~250 (#603). The grid window is **64 cells initially / 96 at full expansion**, which renders reliably where 120+ did not.
  - **204 flood:** category grids are no longer kept mounted behind `use:show`, and exactly one grid is mounted at a time. A hidden grid has a zero-height container, so it believes it is permanently parked at its bottom edge and dispatches `scrolltolower` to JS forever — 599 dispatches over 3 tab switches with 4 kept grids, vs 8 with only the active one (#606).
- `@sigx/lynx-emoji` — switching categories no longer freezes on big categories, and tapping a tab highlights it immediately. `EmojiGrid` renders through a windowed `List` (`@sigx/lynx-list`): the sigx renderer eagerly builds every rendered `<list-item>` subtree (the native recycler only virtualizes views for scrolling), so a switch to people-body previously tore down and rebuilt ~388 cell subtrees in one pass. Switches are two-phase — the tab highlight paints in its own cheap flush, the grid swap follows a tick later — and the grid lays out at full height on its first frame instead of flashing a 1px placeholder (#602, #610).
- `@sigx/lynx-emoji` — the picker no longer renders a fully blank screen on device. `createEmojiContext` now snapshots the dataset to plain objects once (it is static by contract and JSON-born, so the round-trip is lossless): grid items and search entries read proxy-free, dropping deep-proxy read overhead over ~1900 entries (#602).


- `@sigx/lynx-updates` — Android: a purely numeric `updates.runtimeVersion` pin (e.g. `'2'`) made every `checkForUpdate()` report `incompatible`: aapt stores numeric-looking `<meta-data android:value>`s as typed (non-String) values, and the native reader used `Bundle.getString()`, which logs a `ClassCastException` warning and returns null for them — the binary's runtime version read back as `"unknown"`. The reader is now type-tolerant (`get(...)?.toString()`), and `@sigx/lynx-cli` prebuild warns when a pinned runtimeVersion would be re-typed by aapt (already-shipped binaries keep the old reader, and non-canonical forms like `0x1A` or `1e3` still can't round-trip). iOS was unaffected. Note: the fix changes `@sigx/lynx-updates`' Android source content, so auto-computed runtime fingerprints change on next prebuild (#598).
